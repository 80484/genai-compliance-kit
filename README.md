# AI 法学 · 生成式 AI 合规自查工具包

把「一个 AI 产品能不能在国内上线、要办哪些手续、有哪些合规缺口」变成一份**可核对、可整改、可签字**的报告。

当前版本：**v0.1**（规则库 23 条，覆盖中国大陆现行生成式 AI 监管要求）

---

## 这是什么

一个面向**生成式 AI 产品方**的合规自查工具。输入产品事实，输出：

1. **《合规自查报告》** —— 角色认定 → 逐条判定 → 风险等级 → 整改动作
2. **`result.json`** —— 机器可读的判定结果，便于做面板、统计、批量核查

它不替代律师，但能把「上线前该查什么、查到什么程度」这件事标准化，让律师复核的成本从"从零开始"降到"确认与修改"。

---

## 为什么不是个问答机器人

三个设计选择，决定了它和"问 ChatGPT 合规问题"的区别：

**1. 结构化规则库，不用 RAG**

合规判定需要的是**穷举**，不是相似度检索。少召回一条就是一次事故。法条本身「章—条—款—项」就是现成的索引结构，没必要让向量库去猜。

**2. 角色闸门先行**

生成式 AI 生态里，同一项义务对不同主体完全不同。比如内容标识：

| 角色 | 义务 |
|---|---|
| A 模型提供者（自研） | 生成时嵌入标识 |
| B 应用提供者（调 API） | 输出与导出时附加标识 |
| C 传播平台（有发布） | 对他人内容做核验与标注 |
| D 分发平台（应用商店） | 上架前询问并核验标识材料 |

角色判错，后面全部作废。所以第一步不是查法条，是认定角色。

**3. 引用由程序校验，不由模型自证**

模型的头号风险是编造条款号 —— 而且编得非常像真的。所以每一条判定引用的法律名称与条号，都必须**命中规则库**；命中不了就降级为「待核」，并记录"引用异常"。

这一条是整个工具的差异化所在。

## 怎么用

### 方式一：在支持 skill 的 Agent 里直接调用

把 `skills/ai-compliance-check/` 放到 Agent 的 skills 目录，用自然语言触发：

> 帮我做个 AI 产品上线合规自查。产品叫 XX，用户输入主题生成小红书文案，模型是调某云的 API，网页版，还没上线……

Agent 会按 `SKILL.md` 的 7 步走：采集事实 → 角色认定 → 适用性分流 → 逐条判定 → 引用校验 → 汇总 → 自检。

### 方式二：手动跑

1. 按 `references/intake-form.md` 的 Q1–Q5 做角色认定
2. 打开 `rules/v0.1.yaml`，按域逐条过
3. 按 `references/judge-protocol.md` 的四态规则写判定
4. 按 `references/report-template.md` 出报告
5. 最后跑一遍 `judge-protocol.md` 第七节的"报告发出前三问"

### 方式三：程序化调用

`v0.1.yaml` 是标准 YAML，可直接读入：

```python
import yaml
rules = yaml.safe_load(open("rules/v0.1.yaml", encoding="utf-8"))["rules"]

# 按角色过滤
applicable = [r for r in rules if role in r["roles"]]

# 校验引用
known = {(b["law"], b["article"]) for r in rules for b in r["legal_basis"]}
assert (claimed_law, claimed_article) in known, "引用异常，降级为待核"
```

## 判定只有四种状态

| 状态 | 含义 | 必须写清 |
|---|---|---|
| **符合** | 满足通过标准且有证据 | 依据 + 证据出处 |
| **不符合** | 确实没做到 | 缺什么 + 整改动作 + 验收标准 |
| **不适用** | 角色不符 / 触发条件不满足 / 不在服务范围 | 具体理由 |
| **待核** | 材料不足，判不了 | 缺哪份材料 |

`不适用` 和 `不符合` 的法律后果完全不同，混用会毁掉整份报告的可信度。

---

## 三条铁律

1. **无出处不下结论。** 每条判定必须落到「法律名称 + 条号 + 施行日期」，且命中规则库。
2. **不用常识补证据。** 证据不足只能记「待核」。技术类义务须有可复现实证，不能只看口头陈述。
3. **输出是初筛，不是法律意见。** 报告必附免责声明，并保留人工复核栏。

## 规则库覆盖了什么

23 条，六个域：

| 域 | 条目 | 覆盖 |
|---|---|---|
| 主体与准入 | GEN-01~05 | 角色认定、安全评估、算法备案、大模型备案、编号公示 |
| 训练数据 | GEN-06~09 | 来源合法、知识产权、个人信息、标注规范 |
| 内容安全 | GEN-10~13 | 红线内容、歧视性输出、审核与日志、违法内容处置 |
| 标识与透明度 | GEN-14~18 | 显式标识、隐式标识、协议条款、传播核验、分发核验 |
| 个人信息与用户权益 | GEN-19~21 | 输入信息保护、实名认证、未成年人 |
| 服务运营 | GEN-22~23 | 服务协议、投诉举报与服务连续性 |

**已知缺口**（见 `rules/v0.1.yaml` 的 `backlog`）：生物识别编辑的安全评估、单独同意、个人信息权利响应、数据出境、外资准入、ICP 许可、防恶意删除标识、传播平台回写元数据。

遇到规则库没覆盖的问题，工具会输出「规则库未覆盖，建议人工评估」，**不会自创检查项**。

## 数据来源

规则库的每条法条都注明了出处。主要信源：

- 国家法律法规数据库 `flk.npc.gov.cn`
- 中国政府网政策文件库 `gov.cn/zhengce`
- 国家网信办 `cac.gov.cn`（第一信源）
- 算法备案系统 `beian.cac.gov.cn`
- 全国网络安全标准化技术委员会 `tc260.org.cn`
- 北大法宝 `pkulaw.com`、威科先行 `wkinfo.com.cn`（商业库，有 API）

**法规是版本化对象。** 每条都记录施行日期，改版时须同步更新，不能只改条号。

**实务口径必须标注。** 像"大模型备案周期 6–8 个月"这类经验值来自律所实务观察，不是法条，报告里一律标【实务口径，非法定条文】。

## 参与

发现法条引用错误、条文过期、或某条判定口径不对，欢迎提 Issue。最有价值的贡献是这三类：

1. **引用纠错** —— 条号、施行日期、原文摘录不符
2. **口径补充** —— 某地网信办的具体要求、某个行业的特殊规定
3. **误判案例** —— 用这个工具判过、后来发现判错了的真实情形

规则库改动请一并更新 `rules/sources.md` 的台账，并跑一遍：

```bash
python scripts/validate_rules.py
```

## 边界

**能做的**：快速摸清一个产品的合规资产负债表；给出可执行的整改清单；让跨团队沟通有一个共同的事实基础。

**不能做的**：替代律师意见；预判地方监管的个案裁量；处理诉讼与行政处罚应对；覆盖境外法域。

> 本工具输出为自动化初筛结果，不构成法律意见。法规以官方发布文本为准；地方监管口径存在差异且持续变化。对外使用前应由执业律师复核并签署。
