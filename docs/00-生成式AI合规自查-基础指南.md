> 版本 v0.1 ｜ 2026-11-25 ｜ 定位：项目地基文档，不是法律意见

---

## 第 0 章　先把这件事的本质想清楚

### 0.1 合规自查到底是什么

一句话：**判断"我这个产品，在现行规则下必须做什么、不能做什么、做到了没有"。**

它由三个动作串起来，缺一不可：

| 动作 | 问的问题 | 输出的东西 |
|---|---|---|
| 定角色 | 我是谁？ | 义务清单（不同角色义务完全不同） |
| 定规则 | 哪些规范管我？ | 适用规范 + 条款号 + 生效日期 |
| 定证据 | 我拿什么证明我做到了？ | 符合/不符合/不适用/待核 + 证据 |

**最容易犯的错，是跳过第一步直接查法条。** 生成式 AI 生态里至少有四种角色，义务差别极大（见第 2 章）。角色错了，后面全错。

### 0.2 为什么这件事适合用 AI 做

- 规则数量多、条目细、更新快，人脑记不住，但结构稳定
- 判定动作高度重复：同一条款对一百个产品问的是同一个问题
- 需要一致性：人工审容易这次严下次松，机器不会

### 0.3 为什么不能全交给 AI

- **法条记忆不可靠**：模型会编出不存在的条款号。这是这个项目的头号风险。
- **时效判断不可靠**：某条规定有没有被修订、废止，模型不知道。
- **边界情形不可靠**：什么算"具有舆论属性"、什么算"人脸信息"，需要人判断。

所以正确形态是：**AI 做检索、初筛、结构化、成文；人做定性、签字、担责。**

### 0.4 三条铁律（写进 skill，不要动摇）

1. **无出处不下结论。** 每条判定必须能落到"法律名称 + 条款号 + 生效日期"。落不到，标"待核"。
2. **区分"不适用"和"没做到"。** 前者是合法的，后者是风险。混淆这两者，报告就没有价值。
3. **输出是初筛，不是法律意见。** 报告里必须有免责声明和人工复核环节。

## 第 1 章　法规地图：中国现行生成式 AI 监管体系

监管是分层的。写检查项时，一定要标清楚它来自哪一层、效力多高。

### 1.1 四个层级

```
法律层（全国人大及常委会）
├─ 网络安全法（2017.6.1）
├─ 数据安全法（2021.9.1）
├─ 个人信息保护法（2021.11.1）
├─ 科学技术进步法（2022.1.1 修订）
└─ 民法典（人格权编、侵权责任编、合同编相关）

行政法规层（国务院）
├─ 未成年人网络保护条例（2024.1.1）
├─ 网络数据安全管理条例（2025.1.1）
└─ 人工智能综合性立法：立法进程中，尚未出台（2026 年多份官方表态在加快推进）

部门规章层（网信办等）★ 本项目主战场
├─ 互联网信息服务算法推荐管理规定（2022.3.1）
├─ 互联网信息服务深度合成管理规定（2023.1.10）
├─ 生成式人工智能服务管理暂行办法（2023.8.15）
└─ 人工智能生成合成内容标识办法（2025.9.1）

标准/技术文件层（推荐性，但监管实务中当基线用）
├─ TC260-003《生成式人工智能服务安全基本要求》（2024.2）
└─ 各类国标、实践指南（以 TC260 发布为准）
```

### 1.2 核心规章的定位

**《生成式人工智能服务管理暂行办法》**（七部门令第 15 号）——总纲。24 条，管的是"向境内公众提供生成内容服务"的行为。要点：

- 第 2 条：只管**向境内公众提供**的服务。内部研发、不对外提供的，不适用。
- 第 4 条：内容红线（五类：危害国家安全、歧视、侵权、垄断、透明度与准确性）。
- 第 7 条：训练数据五项要求——来源合法、不侵权、个人信息合规、质量、其他法定要求。
- 第 8 条：数据标注规则、质量评估、人员培训。
- 第 9 条：内容生产者责任 + 服务协议。
- 第 10 条：明确适用人群场合用途 + 防未成年人沉迷。
- 第 11 条：输入信息与使用记录保护，最小必要，不得非法留存/提供。
- 第 12 条：按深度合成规定对图片视频标识。
- 第 13 条：服务安全稳定持续。
- 第 14 条：发现违法内容的处置与报告。
- 第 15 条：投诉举报机制。
- 第 17 条：**有舆论属性或社会动员能力的，须安全评估 + 算法备案**。

**《人工智能生成合成内容标识办法》**（2025.9.1 施行）——最新、最容易漏。14 条，核心是"双标识"：

- 显式标识：用户能明显感知（文字提示、语音提示、角标、水印）。
- 隐式标识：写在文件元数据里（生成合成属性、提供者名称/编码、内容编号）。
- 第 6 条：**传播平台**要核验元数据、按情况加提示、提供用户声明功能。
- 第 7 条：**应用分发平台**上架时要问、要核验。
- 第 8 条：标识方法要写进用户协议。
- 第 9 条：提供"无显式标识"版本时，要协议明确用户义务，且**留存日志不少于六个月**。
- 第 12 条：办算法备案、安全评估时要一并提交标识材料。

**《互联网信息服务深度合成管理规定》**——标识义务的原始出处，第 16 条（隐式）、第 17 条（显式）。

**《互联网信息服务算法推荐管理规定》**——备案义务的原始出处，第 24 条（十个工作日内备案）。

### 1.3 时效性提醒

法规有版本。数据结构里必须存：`生效日期`、`失效日期`、`修订沿革`。否则半年后你的报告就是错的。

## 第 2 章　先定角色：四种主体，四套义务

这是整个项目最重要的设计点。**同一个产品，身份不同，义务完全不同。**

| 角色 | 定义 | 核心义务 | 典型主体 |
|---|---|---|---|
| **A. 模型提供者** | 自研模型，直接或经 API 对外提供生成服务 | 训练数据合规、标注规范、安全评估、大模型备案、内容安全 | 大模型厂商 |
| **B. 应用提供者** | 调用他人模型，做成产品对外提供 | 算法备案（若具舆论属性）、标识、用户协议、内容处置、个人信息 | AI 写作/绘画/客服类 App |
| **C. 传播平台** | 提供内容发布与传播服务 | 核验隐式标识、加提示、提供声明功能、处置违法内容 | 社交、社区、短视频 |
| **D. 分发平台** | 应用商店、小程序平台 | 上架时询问是否提供生成合成服务、核验标识材料 | 应用商店 |

**实务中常见组合**：一个产品可能同时是 B + C（自己有社区），或 A + B（自研又做应用）。检查项引擎必须支持多角色叠加。

**判定分流的第一个问题永远是**：

> 你是否向中国境内公众提供生成式人工智能服务？
> - 否 → 本办法不适用（但可能适用数据、个人信息等其他规则）
> - 是 → 你是哪几种角色？

## 第 3 章　把法条变成检查项（方法论核心）

### 3.1 检查项的数据结构

这是规则库的最小单元。建议直接用 YAML 存，便于人读、便于 diff、便于版本管理。

```yaml
- id: GEN-17
  title: 生成式 AI 服务备案
  role: [A, B]                    # 适用角色
  legal_basis:
    - 生成式人工智能服务管理暂行办法 第17条
    - 互联网信息服务算法推荐管理规定 第24条
  effective_from: 2023-08-15
  trigger: 向境内公众提供生成式AI服务，且具有舆论属性或社会动员能力
  question: 是否已完成算法备案（及大模型备案/登记）？
  pass_criteria: 能提供有效备案编号，且备案主体、服务名称与实际一致
  evidence_required:
    - 算法备案编号 + 公示页截图
    - 大模型备案/登记回执（如适用）
  on_fail: 上线前完成备案；未完成不得对外提供服务
  risk: high
  notes: 调用第三方模型的，需提前取得合作方配合材料
```

字段设计要点：
- `role` 决定这条要不要问——不问就是"不适用"，不是"没做到"
- `trigger` 是适用性判断，不是义务本身，这两者要分开
- `evidence_required` 是灵魂：没有证据的"符合"等于没查
- `on_fail` 必须写成动作，不能写"加强合规"

### 3.2 三个真实转换示例

**示例一：训练数据里的个人信息**

法条：《暂行办法》第 7 条第（三）项——"涉及个人信息的，应当取得个人同意或者符合法律、行政法规规定的其他情形"。

转成检查项：

```
问：训练语料中是否包含个人信息（姓名、身份证号、手机号、人脸、声纹、行踪轨迹等）？
若含：
  - 是否取得单独同意？或符合《个保法》第13条其他合法性基础？
  - 是否做了去标识化/匿名化？程度如何？
  - 来源是否可追溯到授权链条？
证据：数据来源清单、授权协议、去标识化处理说明、影响评估报告
判定：符合 / 不符合 / 待核（来源不明即待核，不可判符合）
```

**示例二：生成内容标识**

法条：《标识办法》第 4、5 条。

转成检查项时要拆成两条，因为一个是"看得见"，一个是"看不见"：

```
GEN-ID-01 显式标识
问：文本/图片/音频/视频/虚拟场景，是否在用户可感知位置加了提示？
细项：文本（起末或中间）、音频（语音或节奏提示）、图片（适当位置）、视频（起始画面+播放周边）
证据：各模态产品截图、下载导出后的文件样本
易漏点：下载/复制/导出功能是否保留标识

GEN-ID-02 隐式标识
问：文件元数据中是否写入生成合成属性、提供者名称/编码、内容编号？
证据：元数据读取结果（exiftool 等工具）、技术实现说明
易漏点：只做了前端角标，元数据是空的
```

**示例三：同一件事，角色不同，检查项不同**

"标识"这件事：
- B 应用提供者：我要**加**标识（第 4、5 条）
- C 传播平台：我要**核验**标识、加提示、给用户声明入口（第 6 条）
- D 分发平台：我要**问**开发者、**核验**材料（第 7 条）

如果规则库不区分角色，就会给应用商店开出"你必须在生成的图片上加角标"这种荒谬结论。

### 3.3 判定四态

| 状态 | 含义 | 报告里怎么呈现 |
|---|---|---|
| 符合 | 有证据，且证据支持结论 | 绿色，附证据 |
| 不符合 | 明确缺失或违规 | 红色，附整改动作 + 依据 |
| 不适用 | 触发条件不满足 | 灰色，写明为什么不适用的理由 |
| 待核 | 信息不足，无法判定 | 黄色，列出需要补充的材料 |

**"不适用"要写理由**，这是专业度的体现。写"不适用（未向境内公众提供服务，依据《暂行办法》第2条）"比写"不适用"强十倍。

## 第 4 章　义务全景：六类检查域

按这个分类建规则库，覆盖度容易检查。

### 域一：主体与准入
- 是否向境内公众提供（适用范围判定）
- 算法备案（舆论属性/社会动员能力）
- 大模型备案 or 登记（属地省级网信办）
- 安全评估
- ICP/增值电信业务许可（如涉及）
- 外资准入限制

### 域二：训练数据
- 来源合法性（自有/采购/爬取/开源，各自证明方式不同）
- 知识产权（是否含受著作权保护的作品、有无授权）
- 个人信息（同意/合法性基础/去标识化/影响评估）
- 数据质量（真实性、准确性、客观性、多样性）
- 标注规则、标注质量评估、标注人员培训
- 数据出境（如涉及境外训练）

### 域三：内容安全
- 五类红线内容（第 4 条）
- 歧视性输出（民族、信仰、国别、地域、性别、年龄、职业、健康）
- 违法内容发现—处置—报告闭环（第 14 条）
- 关键词库、测试题库、安全检测模型（TC260-003）
- 生成内容的准确性与可靠性措施

### 域四：标识与透明度
- 显式标识（分模态）
- 隐式标识（元数据）
- 用户协议中的标识条款
- 无标识版本导出的日志留存（≥6 个月）
- 不得恶意删除篡改标识

### 域五：个人信息与用户权益
- 最小必要收集
- 输入信息与使用记录保护（不得非法留存、不得非法提供）
- 查阅/复制/更正/补充/删除请求的处理机制
- 未成年人保护（防沉迷、模式）
- 投诉举报入口、流程、时限

### 域六：服务运营
- 服务协议（权责、适用人群场合用途）
- 服务稳定性与连续性
- 安全管理制度、责任人
- 应急响应与事件报告
- 持续合规（抽检应对）

## 第 5 章　技术架构：怎么在 DSH 里落地

### 5.1 一个反直觉的建议：先别做 RAG

新手第一反应是"把法规灌进向量库做 RAG"。这个思路在这里是错的，原因：

- 合规判定需要的是**穷举**，不是**相似**。检索出"最相关的三条"没有意义，你要的是"所有适用条款"。
- 法条是结构化程度极高的文本，`章-条-款-项` 本身就是索引。
- RAG 的召回率不可控，漏一条就是合规事故。

**正确顺序**：结构化规则库（人工整理，20–50 条）→ 判定工作流 → 报告生成 → 最后才用 RAG 解决"条款解释""监管问答""案例参考"这类开放问题。

### 5.2 三层架构

```
┌─────────────────────────────────────────┐
│  L3  报告层                              │
│  Markdown 报告 + JSON 结构化结果          │
├─────────────────────────────────────────┤
│  L2  判定层                              │
│  适用性分流 → 逐条判定 → 引用校验 → 汇总   │
├─────────────────────────────────────────┤
│  L1  规则层                              │
│  规则库 YAML（检查项 + 法条原文 + 证据要求）│
└─────────────────────────────────────────┘
```

L1 是资产，L2 是能力，L3 是交付物。**L1 的质量决定项目上限**，因为 L2 的模型会换、L3 的模板会改。

### 5.3 为什么用 skill + workflow，而不是插件

| 载体 | 本项目中的角色 |
|---|---|
| **skill** | 判定纪律、检查项清单、报告模板、引用格式、免责话术 |
| **workflow** | 材料解析 → 角色识别 → 适用性分流 → 逐条判定 → 证据核对 → 汇总 → 自检 |
| **plugin** | 等有人要"点一下出报告"时再做；现在做是过早优化 |
| **subagent** | 多个域并行判定时用（六个域互不依赖，天然可并行） |

### 5.4 工作流的关键节点

1. **材料解析**：产品说明、功能清单、数据来源、模型来源、截图 → 结构化事实表
2. **角色识别**：A/B/C/D 单选或多选（这一步决定后面问什么）
3. **适用性分流**：对每个域判断"是否触发"，不触发直接记"不适用 + 理由"
4. **逐条判定**：输入事实表 + 检查项 → 输出四态 + 证据引用 + 缺失材料
5. **引用校验**：把判定里的每个条款号拿去和规则库比对，对不上就打回
6. **汇总**：按风险等级排序，生成整改清单（可执行动作 + 优先级 + 责任方）
7. **自检**：检查是否有"符合但无证据"、是否有"待核未说明原因"

第 5 步是这个项目相对其他 AI 法律产品的核心竞争力——**机器校验自己的引用**。

### 5.5 报告结构建议

```
1. 结论摘要（适用/不适用、高风险项数、能否上线）
2. 主体与角色认定
3. 适用规范清单（名称 + 生效日期 + 适用理由）
4. 逐条自查表（检查项 | 判定 | 依据 | 证据 | 整改）
5. 高风险项专项说明
6. 待补充材料清单
7. 免责声明与人工复核签署栏
```

| 中国裁判文书网 | wenshu.court.gov.cn | 裁判文书 | 网页 | 近年公开量下降，**慎爬** |

### 6.2 商业源（要 API / 要批量时用）

| 来源 | 特点 | 适用 |
|---|---|---|
| 北大法宝 pkulaw.com | 法规 + 案例 + 法学期刊，有 API | 需要批量与结构化时 |
| 威科先行 wkinfo.com.cn | 法规检索，已提供 MCP 服务 | 想快速接工具链时 |
| 法信、Alpha | 案例与实务 | 类案参考 |

**判断标准**：如果只是几十条规则的核对，人工从官方源摘录即可；如果要覆盖几百部法规、做持续更新，再考虑商业 API。

### 6.3 境外源（做对比或出海业务时用）

| 来源 | 内容 |
|---|---|
| EUR-Lex | 欧盟 AI Act 全文与时间表 |
| NIST AI RMF | 美国 AI 风险管理框架 |
| OECD.AI | 各国 AI 政策数据库 |
| 各国监管机构 | UK ICO、新加坡 PDPC、日本 PPC 等 |

### 6.4 数据工程的三个坑

1. **官方库基本没有公开 API**。别指望自动同步，老老实实做"人工摘录 + 版本管理 + 定期复核"。
2. **法规是版本化对象**。存 `生效日期 / 失效日期 / 修订沿革`，不要只存最新文本。报告里引用错版本，等于引用了不存在的法。
3. **裁判文书网不要硬爬**。反爬严格且有合规争议，优先用商业 API 或公开数据集。

### 6.5 自建数据的优先级

按投入产出排序：

1. **规则库**（检查项 YAML）——最高优先级，纯人工，价值最高
2. **法条原文库**（结构化：法律名/条号/款项/文本/生效日期）——从官方源摘录 20–30 部核心规范
3. **备案清单**（已备案的算法/大模型）——从 beian 公示页整理，用于竞品与行业基线
4. **问答对/案例**（监管答复、处罚案例）——用于校准判定口径

## 第 8 章　十个常见错误

1. 不做角色识别，直接套义务清单
2. 把"不适用"写成"不符合"，虚增风险
3. 引用法条不带条款号
4. 引用已废止或未生效的版本
5. 用"建议加强合规"代替整改动作
6. 只查生成式 AI 规章，漏掉《个保法》《数安法》
7. 只查显式标识，漏掉元数据隐式标识
8. 假设所有产品都需要大模型备案（内部使用不需要）
9. 把监管"实务口径"当法定要求写进报告（要标注来源与不确定性）
10. 报告没有免责声明和人工复核环节
