# 生成式 AI 合规自查

## 定位

把「一个 AI 产品是否满足上线前的中国监管要求」变成一份**可核对、可整改、可签字**的报告。

三个不许：
- 不许编造法条、条款号、备案要求
- 不许把"不适用"写成"不符合"，也不许反过来
- 不许给出没有证据支撑的"符合"

输出是**初筛**，不是法律意见。报告必须保留人工复核与免责声明。

---

## 铁律（任何情况下不得违反）

1. **先定角色，再查义务。** 角色错，全盘错。
2. **无出处不下结论。** 每条判定必须落到「法律名称 + 条号 + 施行日期」，且该条必须存在于 `rules/v0.1.yaml`。
3. **证据不足只能记「待核」。** 不允许用常识、类比、行业惯例补足证据。
4. **区分三种"没做到"**：真违规（不符合）、条件不满足（不适用）、信息缺失（待核）。三者的法律后果完全不同。
5. **整改建议必须是动作。** 能派活、能验收、有时限。禁止"加强合规意识""完善管理制度"这类空话。

## 工作流

### 第 1 步 · 采集事实

按 `references/intake-form.md` 收集材料。至少需要：

- 产品是什么、给谁用、在哪些渠道分发
- 模型来源（自研 / 调 API / 开源微调）
- 有没有用户内容发布功能
- 生成哪些模态（文本/图片/音频/视频/虚拟场景）
- 训练数据来源（若自研）
- 已有的备案、评估、标识实现

材料不足时**不要猜**。把缺口列成"待补充材料清单"，相关条目判「待核」。

### 第 2 步 · 角色认定（闸门）

回答《暂行办法》第 2 条：是否向境内公众提供生成式 AI 服务？

- 否 → 生成"不适用说明"，注明仍可能适用的其他规范（个保法、数安法、广告法等），结束主流程
- 是 → 认定角色，可多选：

| 角色 | 判据 |
|---|---|
| A 模型提供者 | 自研模型，以自己名义对外提供（含 API） |
| B 应用提供者 | 调用他人模型做成产品 |
| C 传播平台 | 有用户内容发布/传播功能 |
| D 分发平台 | 自己是应用商店/小程序平台 |

**多角色要叠加义务，不是二选一。**

### 第 3 步 · 适用性分流

对 `rules/v0.1.yaml` 的每一条：

1. `roles` 不含已认定角色 → **不适用**，写明理由（引用该条 `legal_basis` 或角色定义）
2. `trigger` 不满足 → **不适用**，写明哪个条件不满足
3. 满足 → 进入判定

不要跳过这一步直接判定。分流记录本身是报告价值的一部分。

### 第 4 步 · 逐条判定

对每条进入判定的检查项，输出：

```
判定：符合 / 不符合 / 待核
依据：法律名称 第X条（必须能在规则库中命中）
事实：材料里的哪句话/哪张图支撑这个判定
证据缺口：缺什么材料（判定为待核或符合但证据薄弱时必填）
整改：具体动作 + 优先级 + 建议责任方（不符合时必填）
```

判「符合」的门槛：`evidence_required` 中的每一项都能在材料里找到对应物，或明确说明为何不适用。

### 第 5 步 · 引用校验（不可省略）

逐条检查：

- 引用的法律名称是否在规则库中
- 条号是否在规则库中该法律的条目里出现
- 施行日期是否与规则库一致
- 是否引用了规则库 `backlog` 中的条目却当成已覆盖

任一不通过 → 该条判定降级为「待核」，并记录"引用异常"。

**这一步是这个工具相对通用问答的核心差异。不要因为"看起来对"就跳过。**

### 第 6 步 · 汇总

- 按风险等级排序：high → medium → low
- 高风险项单列，写清"不整改的后果"
- 生成整改清单：动作 / 优先级 / 建议责任方 / 验收标准
- 统计：符合 X 条，不符合 Y 条，不适用 Z 条，待核 W 条

### 第 7 步 · 自检

逐项确认：

- [ ] 有没有"符合"但 `evidence_required` 没被满足的条目
- [ ] 有没有"待核"但没写清缺什么
- [ ] 有没有"不适用"但没写理由
- [ ] 有没有引用规则库之外的法条
- [ ] 整改建议是否都能派活
- [ ] 免责声明与人工复核栏是否在

## 判定协议

四态定义、证据分级、边界情形处理，见 `references/judge-protocol.md`。遇到以下情形必须先读它：

- 判断"是否具有舆论属性或社会动员能力"
- 判断"是否向境内公众提供"
- 判断某材料是否构成充分证据
- 判断某个实务口径（如各地网信办备案要求）能否写进结论

## 输出

### 主交付物

按 `references/report-template.md` 生成 Markdown 报告：

```
compliance-reports/<产品名>-<YYYYMMDD>/report.md
```

### 机器可读结果（便于后续做面板/统计）

同目录 `result.json`：

```json
{
  "product": "",
  "date": "YYYY-MM-DD",
  "roles": ["B"],
  "summary": { "pass": 0, "fail": 0, "na": 0, "pending": 0 },
  "items": [
    {
      "id": "GEN-14",
      "status": "fail",
      "basis": "人工智能生成合成内容标识办法 第4条",
      "evidence": "导出图片无角标，元数据为空",
      "gap": "导出链路未加标识",
      "action": "在导出管线增加角标合成，验收标准：导出文件可见标识"
    }
  ],
  "high_risks": ["GEN-03", "GEN-14"],
  "pending_materials": []
}
```

字段约束：
- `status` 只能是 `pass` / `fail` / `na` / `pending`
- `id` 必须来自规则库
- `basis` 必须命中规则库

## 报告里必须出现的话

> 本报告为自动化初筛结果，不构成法律意见。法规以官方发布文本为准；地方监管口径存在差异且持续变化。对外使用前应由执业律师复核并签署。
