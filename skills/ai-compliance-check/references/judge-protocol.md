# 判定协议（Judge Protocol）

> 这份文件解决一个问题：**同一个事实，不同的人判出不同结论时，按什么标准收敛。**
> 凡是本文没有覆盖的情形，一律判「待核」，不许自由裁量。

---

## 一、四态的精确定义

判定从"该不该问"开始，分两段：先判适用性，再判合规性。

```
该条 roles 是否包含已认定角色？
├─ 否 ────────────────────────────→ 不适用（写明角色不符）
└─ 是 ─→ trigger 是否满足？
         ├─ 否 ───────────────────→ 不适用（写明哪个触发条件不满足）
         └─ 是 ─→ 证据是否足以支撑结论？
                  ├─ 否 ──────────→ 待核（写明缺什么材料）
                  └─ 是 ─→ 是否满足 pass_criteria？
                           ├─ 是 ─→ 符合
                           └─ 否 ─→ 不符合
```

### 四态的写法要求

| 状态 | 必须包含 | 禁止 |
|---|---|---|
| **符合** | 依据条款 + 证据出处 + 证据类型 | 只写"已具备" |
| **不符合** | 依据条款 + 缺什么 + 整改动作 + 验收标准 | 只写"存在问题" |
| **不适用** | 不适用的具体理由（角色不符 / 触发条件不满足 / 服务范围） | 只写"不适用" |
| **待核** | 缺哪份材料 + 拿到后能判什么 | 只写"需进一步确认" |

### 「不适用」的三种合法理由

1. **主体不适用**：角色不在该条 `roles` 内（如 D 类分发平台不承担显式标识义务）
2. **行为不适用**：`trigger` 不满足（如未开展预训练 → 训练数据条款不适用）
3. **范围不适用**：服务未向境内公众提供（依据《暂行办法》第 2 条）

**不适用不是"免检"。** 每条不适用都要能回答"如果我以后加了 X 功能，这条会变成适用吗"，并写进报告的"变更提示"。

## 二、证据分级

判定"符合"需要证据。证据分四级，**技术类义务必须达到 E2**。

| 级别 | 类型 | 举例 | 可支撑的结论 |
|---|---|---|---|
| **E1** | 官方文书 | 备案编号与公示页、备案回执、评估报告签章页 | 可直接判符合 |
| **E2** | 可复现的实证 | 导出文件的元数据读取结果、产品界面截图、接口返回 | 可直接判符合 |
| **E3** | 书面制度 | 内容审核 SOP、标注规则、应急预案、数据来源清单 | 制度类义务可判符合；技术类只能判待核 |
| **E4** | 口头/邮件陈述 | "我们做了""应该是有的" | **不能判符合**，最多判待核 |

### 硬规则

- 标识类（GEN-14/15/17）：必须 E2。截图和导出文件缺一不可。
- 备案类（GEN-03/04）：必须 E1。
- 训练数据类（GEN-06/07/08）：E3 可接受，但需附"执行留痕"（清洗记录、合同、授权文件）。
- 任何"用户说做了但拿不出东西"的情况 → 待核。

### 一条容易忽略的判据

**证据的时点。** 三个月前的截图只能证明三个月前合规。若产品在此期间有重大功能更新，相关条目降为待核。

## 三、四个高频边界情形

### 3.1 是否"向境内公众提供"

判"是"，只要满足任一：

- 有面向不特定人的公开访问入口（应用商店、官网、小程序、公开注册）
- 虽需邀请码，但邀请可自由扩散且无实质审核
- 通过 API 向外部开发者提供

判"否"，需要同时满足：

- 仅限特定组织内部人员
- 有实质的身份核验与访问控制
- 不对外提供任何形式的开放注册

**灰色地带**（如"内测 100 人"）：若测试用户来自外部且内容可外传，倾向判"是"。不确定时按更严口径判，并在报告中说明。

### 3.2 是否"具有舆论属性或社会动员能力"

《暂行办法》《算法推荐规定》均未定义。实务参照《具有舆论属性或社会动员能力的互联网信息服务安全评估规定》的列举：

- 论坛、博客、微博客、聊天室、通讯群组、公众账号、短视频、网络直播、信息分享、小程序等
- 提供公众舆论表达渠道，或具有发动社会公众从事特定活动能力的其他服务

**判断要素**（命中越多越可能构成）：

1. 内容是否可被不特定多数人获取
2. 是否形成公开的意见表达或讨论空间
3. 是否具备快速扩散机制（转发、推荐、分享）
4. 用户规模与影响面

**判定纪律**：这是**法律定性**，不是事实核对。报告里必须写"构成/可能构成/不构成 + 理由 + 建议由律师确认"，不能只写"是"或"否"。

### 3.3 什么算"显著标识"

《标识办法》第 4 条只写"显著"，未给尺寸。判断要素：

- 用户**无需额外操作**即可感知（不用滚动、不用点开、不用悬停）
- 不与背景混淆，不被界面元素遮挡
- 在导出/分享后的载体上依然存在
- 文字提示的表述能让普通用户理解"这是 AI 生成的"

反之：藏在折叠区、只在设置页说明、只在加载动画里闪一下 —— **不构成显著**。

### 3.4 实务口径能不能写进结论

**不能直接写成"法定要求"。** 必须标注来源与不确定性，格式：

> 【实务口径，非法定条文】据多地网信办备案实践，大模型备案周期约 6–8 个月，需提交拦截关键词列表与测试题库。具体要求由属地网信办掌握，存在地区差异，请以当地口径为准。

三类需要这样标注的：大模型备案/登记的材料清单与周期、各地安全评估的具体要求、备案编号在应用商店的提交时点。

## 四、整改动作的写法

**公式**：`动词 + 对象 + 交付物 + 验收标准 + 时限`

不合格的写法：

- ❌ 完善内容安全管理制度
- ❌ 加强标识
- ❌ 建议尽快备案
- ❌ 提高合规意识

合格的写法：

- ✅ 在导出管线（`export/render.ts`）增加角标合成步骤；交付物：3 个模态的导出样例文件；验收：用系统看图工具可见角标，且 `exiftool` 能读到 `AIGC=1` 与提供者编码；时限：上线前 5 个工作日
- ✅ 在备案系统提交算法备案；交付物：备案编号与公示页链接；验收：编号在备案系统可查且主体名称一致；时限：上线前（预留 3 个月）
- ✅ 在用户协议第 6 条增加标识条款；交付物：协议 diff；验收：含"标识方法、样式、用户义务"三要素；时限：本周

### 优先级规则

| 优先级 | 判据 |
|---|---|
| P0 | 会导致不予备案、下架、行政处罚 |
| P1 | 检查中大概率被要求整改 |
| P2 | 形式补正，可并行 |

## 五、引用校验规则

每次判定后，逐条跑：

1. 法律名称在 `rules/v0.1.yaml` 的 `legal_basis` 中出现过？
2. 条号在该法律的条目里出现过？
3. 条目的 `effective_from` 与规则库一致？
4. 引用的是否属于 `backlog`（未收录）？
5. 是否引用了规则库之外的规范（如《广告法》）却没有来源？

任一项不通过：

- 该条判定降为「待核」
- 在报告"引用异常"小节记录：`条目ID / 声称的引用 / 异常类型`
- 不要试图"修正"成一个看起来合理的条号 —— 这是最危险的行为

### 一个必须接受的现实

规则库只有 23 条，覆盖不了所有情形。遇到规则库没有的问题：

> 规则库未覆盖该情形，建议人工评估。相关规范可能涉及：<列出方向，不写条号>

**宁可不答，不可编造。**

## 六、常见误判清单

自查报告发出前，逐条比对：

| # | 误判 | 正确做法 |
|---|---|---|
| 1 | 调用第三方模型 → 认为不用备案 | 提供服务的仍是你，算法备案义务在你 |
| 2 | 产品有社区功能，但只按 B 类判 | 叠加 C 类，加传播平台核验义务 |
| 3 | 界面有 AI 角标 → 判标识合规 | 还要验导出文件与元数据 |
| 4 | 有用户协议 → 判协议合规 | 还要看是否含标识条款、是否留同意痕迹 |
| 5 | 内部试用 → 判全部不适用 | 先判是否构成"向公众提供" |
| 6 | 把"待核"写成"不符合" | 虚增风险，会让报告失去可信度 |
| 7 | 把"不适用"写成"符合" | 掩盖未来风险，变更后会翻车 |
| 8 | 引用已废止版本 | 核对 `effective_from` 与现行文本 |
| 9 | 把行业惯例当法定要求 | 标注【实务口径】 |
| 10 | 报告没有免责声明 | 必须加，且在显著位置 |

## 七、报告发出的最后一道门

在生成报告前，回答三个问题。任一答不上来，不要发：

1. 这份报告里，**哪一条最可能被律师推翻？** 为什么？
2. 如果监管明天来检查，**哪一个"符合"最容易被证伪？**
3. 报告里有没有**任何一句是在没有材料的情况下写出来的？**

第三问只要有一个"是"，就回去把那句改成「待核」。
